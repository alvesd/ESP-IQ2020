# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A fork of [Ylianst/ESP-IQ2020](https://github.com/Ylianst/ESP-IQ2020) (git remote `upstream`; the fork's work is on branch `mobile-app`). The goal is to control an IQ2020 hot tub from iPhone/Android apps that talk **directly** to the ESP32, without Home Assistant.

```
Spa IQ2020 board ──RS485 38400 8N1── ESP32 (ESPHome + components/iq2020) ──ESPHome native API, TCP 6053, Noise──► app/ (Flutter)
```

Home Assistant was only ever one client of ESPHome's native API. The `iq2020` component has no Home Assistant-specific logic (it includes `CustomAPIDevice` but registers no services), so the app talks to the same entities Home Assistant does.

## Layout

- `components/iq2020/`: the ESPHome external component from upstream (C++ plus Python codegen). `components/iq2020-dev` and `components/iq2020-legacy` are upstream variants; edit `iq2020` unless told otherwise. Keep changes here minimal and upstream-friendly so the fork can keep merging `upstream/main`.
- `firmware/hot-tub-mobile.yaml`: the ESPHome config for running without Home Assistant. Secrets go in `firmware/secrets.yaml` (git-ignored; see `secrets.example.yaml`).
- `app/`: the Flutter app. `ios/` and `android/` are generated by `app/tool/bootstrap.sh` and aren't hand-written.
- `documentation/`: upstream protocol notes. `protocol.md` describes the RS485 frame format and bus addresses; the per-module docs cover salt, Coolzone, audio and so on.
- `DataViewer/`: upstream C# tool for viewing raw RS485 captures. Not related to the app.

## Commands

Firmware (needs ESPHome: `pip install esphome`):
```bash
esphome config firmware/hot-tub-mobile.yaml     # validate
esphome run firmware/hot-tub-mobile.yaml        # build + flash (USB first time, then OTA)
esphome logs firmware/hot-tub-mobile.yaml
```

App (needs Flutter 3.22 or later):
```bash
cd app && ORG=com.yourname ./tool/bootstrap.sh   # first time: generate ios/android + permissions
cd app && flutter analyze
cd app && flutter test
cd app && flutter test test/protocol_test.dart --plain-name 'noise'   # run a single test group
cd app && flutter run
```

Talking to a real device from the command line (independent of the Dart client): `pip install aioesphomeapi` then `aioesphomeapi-logs --noise-psk '<key>' hot-tub.local`.

## Firmware architecture (components/iq2020)

- `IQ2020Component` (`iq2020.cpp`) owns the UART. `loop()` reads bytes into a ring buffer, and `processIQ2020Command()` parses frames (`1C dst src len flags data… checksum`). It polls the spa every `polling_rate` seconds with `pollState()` and publishes to sensor pointers set from the YAML.
- The entity platforms (`switch/`, `fan/`, `climate/`, `select/`, `number/`, `text/`, `button/`) are thin wrappers. They call back into the global `g_iq2020_main` (`switchAction`, `setTempAction`, `numberAction`, `setCoolzoneMode`, …) and are addressed by `datapoint` index (the `SWITCH_*`, `SELECT_*`, `NUMBER_*` defines in `iq2020.h`).
- Each platform has two halves: `__init__.py`/`sensor.py` (the config schema plus codegen that calls the C++ setters) and the C++ class. A new sensor needs both a schema entry and a `set_*_sensor` setter.
- The ESP32 can impersonate missing bus modules: `ace_emulation`, `audio_emulation` and `freshwater_emulation`.
- The optional `port:` opens an **unauthenticated** raw RS485 TCP bridge (anything a client sends goes straight onto the bus). It's for DataViewer debugging only. Never enable it in the mobile firmware, and never build app features on it.
- The Coolzone heat pump is exposed as climate mode (Heat, Cool = "Chill", Auto) plus a BOOST or ECO preset, which maps to mode bytes 0x00–0x04.

## Mobile firmware rules (firmware/hot-tub-mobile.yaml)

- `api.reboot_timeout: 0s` is required. ESPHome's default reboots the ESP32 every 15 minutes when no API client is connected, which is the normal state without Home Assistant.
- Time comes from `sntp`, not `homeassistant`.
- ESPHome derives an entity's `object_id` from its **name**, not its YAML `id`. The app groups entities by type and only uses object IDs as hints (icons, headline sensors).

## App architecture (app/lib)

- `api/esphome_client.dart`: `EspHomeClient` (a `ChangeNotifier`), one instance per open spa screen. The sequence is: TCP connect → Noise hello/handshake → `HelloRequest` + empty `AuthenticationRequest` → `DeviceInfoRequest` → `ListEntitiesRequest` until `ListEntitiesDone` → `SubscribeStatesRequest`. It must answer `PingRequest`, `GetTimeRequest` and `DisconnectRequest`, pings every 20 s, treats 60 s of silence as dead, and reconnects with backoff. Sends are serialized through `_sendChain` because the Noise nonces must stay in order.
- `api/noise.dart`: hand-written `Noise_NNpsk0_25519_ChaChaPoly_SHA256` using `package:cryptography`, prologue `NoiseAPIInit\0\0`. Noise framing is `0x01, len_hi, len_lo`, and the encrypted payload is `type(2) len(2) protobuf`. The client opens with an empty frame (`01 00 00`), then `0x00 + handshake msg1`. The server replies with a hello frame (`0x01`, name\0, mac\0), then a handshake frame (`0x00 + msg2`, or a non-zero byte + an error string). The reference implementation is aioesphomeapi `_frame_helper/noise.py`.
- `api/messages.dart` and `api/protobuf.dart`: no protoc or codegen. Message IDs and field numbers are copied by hand from `esphome/components/api/api.proto`. When adding a message or field, look it up there (field numbers aren't sequential, and number 4 is often skipped). Proto3 zero values are omitted on the wire, so command messages need their `has_*` flags.
- `ui/spa_screen.dart` builds the whole UI from the reported entities (climate card, a jets tile per fan, then switches, selects, numbers, sensors and status). Entities with `disabled_by_default` are hidden, and config/diagnostic ones go under "Device & diagnostics". Don't hard-code a fixed set of hot tub features: models differ in jets, °F/°C, salt, Coolzone and audio.
- `device_store.dart`: saved devices and their API keys are kept in `flutter_secure_storage`. Discovery uses `bonsoir` for `_esphomelib._tcp`; iOS needs `NSLocalNetworkUsageDescription` and `NSBonjourServices`, which `bootstrap.sh` adds.

## Known gaps

- The Dart Noise handshake and transport match the reference Python `noiseprotocol` 0.3.1 library byte for byte (`test/noise_interop_test.dart`, using fixed ephemeral-key vectors). The TCP framing, the message sequence and the UI haven't been tested against a real ESPHome device yet.
- Remote access (outside home Wi‑Fi) isn't implemented. The intended options are a user VPN (Tailscale/WireGuard) or ESPHome `mqtt:` to a hosted broker. Never port-forward 6053 or the RS485 bridge port.
